# Orbis Control — DECISIONS

## D-001: GitHub main — canonical baseline

Решение:

Не продолжать работу вслепую в старом local checkout с неизвестным состоянием.

Если текущий checkout не доказанно чистый и синхронизированный, сохранить его нетронутым и создать свежий sibling clone GitHub `main`.

Почему:

Это безопаснее, чем переименовывать, очищать или удалять неизвестный repository, и исключает влияние старых незакоммиченных экспериментов.

---

## D-002: Сохраняем Rust + Slint и текущие privilege boundaries

Решение:

Не переписывать Orbis Control и не менять основной stack/daemon boundaries без доказанной необходимости.

Почему:

Существующий проект уже содержит production paths, tests и hardware safety invariants. Переписывание не решает текущую проблему завершённости продукта и резко увеличивает regression risk.

---

## D-003: Новый набор документов — источник истины текущей итерации

Решение:

Для текущей продуктовой итерации:

- `SPEC.md` — требования продукта;
- `ACCEPTANCE.md` — объективные критерии готовности;
- `IMPLEMENTATION_PLAN.md` — execution queue;
- `DECISIONS.md` — устойчивые решения.

Эти документы имеют приоритет над старыми roadmap/completion documents для пересекающегося scope.

Старый `FINISH_PLAN.md` нельзя использовать как параллельную независимую очередь задач.

Если `AGENTS.md` или другие инструкции отправляют агента в `FINISH_PLAN.md`, необходимо минимально обновить такие ссылки, чтобы для текущего scope существовала одна активная execution queue.

Почему:

Несколько параллельных roadmap создают противоречия и провоцируют работу над планированием вместо реализации.

---

## D-004: TDP представлен реальными hardware fields

Решение:

Не вводить единое синтетическое значение TDP.

Показывать реальные SPL/SPPT/FPPT и другие capability fields отдельно.

Почему:

Они имеют разные hardware semantics, диапазоны и lifecycle. Объединение ухудшает точность, read-back и диагностику.

---

## D-005: Capability-driven вместо model-driven

Решение:

Controls появляются и становятся writable на основании runtime evidence.

Почему:

Одинаковая модель ноутбука не гарантирует одинаковый firmware/driver/backend interface. Проект уже использует capability-oriented approach.

---

## D-006: Существующий audited UI — базовый visual language

Решение:

Не проектировать новый интерфейс с нуля.

Использовать существующие audited Slint pages, Palette и components и исправлять конкретные visual/UX defects.

Почему:

Основная проблема — законченность реализации и качество конкретных состояний, а не отсутствие ещё одной дизайн-концепции.

---

## D-007: Real hardware validation отделена от implementation

Решение:

Реальные hardware writes не являются обязательными для продолжения разработки, пока пользователь отдельно их не разрешил.

Почему:

Software path можно реализовывать и проверять через unit, fixture, private-D-Bus и P2P integration tests. Отдельное разрешение требуется для утверждения, что конкретная mutation live-validated на физическом устройстве.
