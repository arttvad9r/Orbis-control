# ADR 0003: GPU Provider Strategy

- Статус: **Принято** (Этап 0/1, 2026-08-06)
- Дата: 2026-08-06

## Контекст

G-Helper предоставляет четыре GPU-кнопки: Eco, Standard, Ultimate, Optimized.
В Linux нет единого «GPU mode»: физический MUX, доступ приложений к dGPU и
фактическое энергопотребление — разные сущности с разными интерфейсами.
Несколько backend-ов: asusd/asus-armoury, supergfxd, cardwire, стандартный PRIME.
Требуется ранжируемая стратегия без привязки бизнес-логики к конкретному проекту
и честное отображение того, что реально поддерживается.

## Решение

1. **Разделение на три независимые сущности** (три под-провайдера):

   - `MuxProvider` — физический MUX (переключение видео-выхода внутреннего
     дисплея). Единственный, кто может дать «Ultimate».
   - `GpuAccessProvider` — доступ приложений к dGPU (блокировка/разблокировка).
   - `GpuPowerStateProvider` — фактический power state dGPU (read-only телеметрия).

   Никогда не объединять их в одно булево значение. UI показывает состояние
   каждой сущности отдельно, даже когда кнопка одна.

2. **Ранжирование backend-ов:**

   - MUX: asusd `AsusArmoury/gpu_mux_mode` (1) → kernel asus-nb-wmi `gpu_mux_mode`
     через hardwared (2) → supergfxd (3, legacy).
   - Access: Cardwire (экспериментальный, Wayland-only) (1) → asusd
     `dgpu_disable` (2) → supergfxd integrated (3, legacy) → read-only режим (4).
   - Power state: sysfs/DRM (1) → supergfxd `Power()` (2) → NVML/nvidia-smi
     read-only (3) → cardwire `power_state` (4).

3. **Cardwire помечается Experimental** до подтверждения стабильности конкретной
   версии; UI явно показывает, что его «блокировка dGPU» ≠ физический MUX.

4. **supergfxd — legacy fallback**, не первый выбор на системах с asusd.

5. **Optimized — политика, а не аппаратный режим**: реализуется в sessiond
   (автоматизация): battery → Eco-намерение, AC → Standard; configurable delay;
   защита от дребезга; при внешнем мониторе на dGPU — не отключать; при активных
   вычислениях — отложить переключение; показывать фактический подрежим.

6. **Eco перед переключением проверяет**: использование dGPU приложениями;
   внешние мониторы на dGPU; CUDA/ROCm/Vulkan процессы; владельца внутреннего
   дисплея; требование logout/reboot.

7. **Ultimate**: кнопка только при наличии MUX; диалог до применения; точное
   требование reboot/logout; pending state; отмена pending, если backend позволяет;
   не отображать активным до подтверждения фактического состояния после загрузки.

## Обоснование

- На исследованной системе (FA707NV, ядро 7.1.6, asusd 6.3.8) реально доступны:
  `gpu_mux_mode` (MUX, possible [0,1]), `dgpu_disable` (possible [0,1]) — оба через
  asusd AsusArmoury. Cardwire отсутствует, supergfxd активен.
- Разделение сущностей подтверждено эмпирикой: MUX-значение защёлкивается
  firmware (reboot), dgpu_disable мгновенно, block через eBPF — третье поведение.
- Наследование булева «GPU on/off» из Windows-мира в Linux некорректно и
  приводило бы к ложным обещаниям.

## Последствия

- Положительные: честная capability-модель; UI не врёт; безопасность (проверки
  перед Eco); миграция между backend-ами без смены бизнес-логики.
- Отрицательные: сложнее модель данных (три провайдера GPU); требует аккуратного
  UI, чтобы четыре кнопки остались компактными.
- Риски: пользователь путает «Eco» (block) и «Ultimate» (MUX) — смягчается
  tooltip-ами и детальным статусом в подзаголовке кнопки.
- Открыто: политика для Optimized при активных вычислениях (delay/предложение
  отложить) — детали в Этапе 5.
