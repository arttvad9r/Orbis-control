# ADR 0002: Daemon Boundaries (sessiond vs hardwared vs GUI)

- Статус: **Принято** (Этап 0/1, 2026-08-06)
- Дата: 2026-08-06

## Контекст

Приложение должно: работать без открытого GUI; не требовать root для GUI; иметь
единый источник состояния; поддерживать автоматизацию; корректно работать при
отсутствии части сервисов; не создавать «универсальный root-демон». Нужно
определить границы между компонентами.

## Рассматривавшиеся варианты

1. **Всё в GUI** — просто, но нарушает «работает без GUI», смешивает UI и бизнес-
   логику, GUI обязан держать D-Bus подписки.
2. **Один root-демон на всё** — нарушает «GUI не от root», создаёт большой
   привилегированный компонент (против правил безопасности и threat model).
3. **GUI + sessiond (user daemon), без root-компонента** — покрывает 95 % функций,
   т.к. asusd/UPower/существующие сервисы уже предоставляют root-функции.
4. **GUI + sessiond + универсальный root helper «на всякий случай»** — отвергнуто:
   увеличивает атакуемую поверхность без необходимости.

## Решение

Три компонента с чёткими границами:

- **orbis-ui (GUI)** — только представление; никакого HW I/O, никакого root,
  общается исключительно с sessiond по session bus.
- **orbis-sessiond (user daemon)** — владелец состояния, агрегатор провайдеров,
  автоматизация, pending actions, D-Bus API для GUI/CLI. Работает без GUI.
- **orbis-hardwared (root helper)** — **не создаётся по умолчанию**. Добавляется
  только когда конкретная обязательная функция:
  1. не предоставляется asusd;
  2. не предоставляется стандартным системным D-Bus;
  3. не может безопасно выполняться непривилегированным пользователем;
  4. имеет стабильный kernel ABI;
  5. требует узкой привилегированной операции.

Обоснование:

- На исследованном стеке (asusd 6.3.x + asus-armoury + UPower + fwupd + logind +
  supergfxd) root-граница уже закрыта системными сервисами: у sessiond нет
  причин писать sysfs в root-зоне.
- Снижение атакуемой поверхности: единственный root-компонент — минимальный,
  allowlist, polkit, sandbox (см. threat-model).
- Автоматизация и состояние живут на уровне пользователя — переживают закрытие GUI.
- Пользовательский демон корректно завершается при logout через systemd user unit.

## Последствия

- Положительные: GUI без привилегий; демон переживает GUI; fallback провайдеров;
  чёткие интерфейсы; тестируемость (mock sessiond).
- Отрицательные: два D-Bus слоя (session API + system сервисы); усложнение
  упаковки (user unit + опционально system unit + polkit).
- Риски: рассинхронизация версий API sessiond/GUI — решается единым типовым
  crate (`orbis-core` + zbus XML), версионированием интерфейса
  (`io.github.orbiscontrol.Session1`).
- Решение пересматривается при добавлении функции, требующей root: сначала
  проверяется системный сервис, потом — решение о hardwared (ADR-запись).

## Статус на текущий момент

hardwared: **не создаётся**. При необходимости (например, write
`charge_control_end_threshold` без asusd на read-only системах) — отдельный ADR и
реализация с полным набором требований §5.4.

## Amendment — hardwared введён (2026-08-09 / 2026-08-13)

Положение данного ADR о том, что `orbis-hardwared` не создаётся, было корректным
для момента его принятия (Этап 0/1, 2026-08-06). Оно было **частично superseded**
более поздними решениями:

- [ADR 0006](0006-privileged-performance-write.md) — ввёл `orbis-hardwared` для
  первой доказанной privileged capability (Performance profile write);
  `orbis-hardwared` добавлен в workspace members.
- [ADR 0007](0007-battery-mutation-backend.md) — добавил Battery charge-limit
  mutation через typed asusd D-Bus setter в hardwared.
- [ADR 0008](0008-supergfxd-staged-gpu-mutation.md) — зафиксировал staged GPU
  mutation contract через hardwared (live mutation не реализована).

Остальные принципы ADR 0002 (GUI без root, sessiond как user daemon, hardwared
как узкий helper с allowlist/polkit/sandbox, каждая новая capability требует
отдельного ADR) остаются действующими.
