# Orbis Control dependency audit — 2026-08-19

Scope: backlog item #77. Audit unused/duplicate direct Rust dependencies, feature flags and lock consistency without broad dependency upgrades.

## Result

The audit found a small behavior-neutral cleanup candidate in `orbis-ui`, but publishing it as a normal implementation PR is currently **BLOCKED** by pre-existing workspace/toolchain compatibility issues discovered during targeted validation.

## `orbis-ui` direct dependency findings

The current `crates/orbis-ui/Cargo.toml` declares direct dependencies on `clap`, `serde` and `serde_json`.

A full source scan of the active UI crate entrypoints/modules/examples (`main.rs`, `composition.rs`, `controller.rs`, `worker.rs`, `lib.rs`, `examples/ui_snapshot.rs`) found no direct use of those three crates. CLI argument parsing in `main.rs` is manual rather than `clap`-based.

Candidate behavior-neutral cleanup: remove those three direct declarations from `orbis-ui` only. They may remain in `Cargo.lock` or the overall resolved graph when required transitively/by other workspace crates; therefore their continued lock presence is not evidence that the UI direct declarations are needed.

Other audited UI dependencies have direct source/build roles and are not removed by this audit.

## Validation attempt

A candidate branch `agent/ui-dependency-cleanup` was validated through a disposable exact-SHA workflow. No permanent implementation PR was opened.

### Pre-existing manifest compatibility issue

The hardening `orbis-ui/Cargo.toml` contains a multi-line inline table for the `orbis-providers` dependency. Repository Rust is pinned to channel `1.85`. Cargo 1.85 rejected that existing syntax during the first validation attempt.

The candidate branch normalized that one declaration into a single-line inline table without changing dependency semantics, solely to allow the intended dependency cleanup to be evaluated.

### Pre-existing Rust/dependency compatibility issue

With the corrected manifest, exact implementation SHA and exact one-file scope checks passed and Cargo proceeded deep into the UI dependency graph. Compilation then failed in external registry crate `fontdue 0.9.4`, which uses `integer_sign_cast` APIs that are unstable/unavailable on the repository-pinned Rust 1.85 toolchain.

This failure is outside the three-direct-dependency cleanup scope. Resolving it would require a deliberate repository-level dependency/toolchain decision (for example, compatible dependency resolution or a supported Rust-version change) and therefore is not folded into this behavior-neutral audit.

## Cargo.lock conclusion

No `Cargo.lock` edit is proposed for removal of the three UI direct dependencies. The validation download graph still contained `clap`, `serde` and `serde_json` through other/transitive requirements. Lock pruning/updating must be driven by a successful workspace resolution, not hand-edited to make the audit diff smaller.

## Feature flags

The audit did not remove the UI `mock` feature or the current `orbis-providers` `mock` feature edge. That path is architectural/test behavior rather than an obviously unused direct dependency and must be handled by the separate production-mock cleanup plan, not opportunistically here.

## Required follow-up

1. Resolve the Rust 1.85 / UI dependency graph compatibility issue as its own dependency/toolchain slice.
2. Re-run targeted `orbis-ui` check/tests/clippy on the cleanup candidate.
3. Only then publish the dependency-removal implementation PR if green.
4. Keep `Cargo.lock` generated by Cargo; never edit dependency resolution manually.

## Evidence classification

The unused-direct-dependency finding is source-audit evidence. The implementation candidate is not accepted because compile/test/clippy validation is blocked. No live hardware, D-Bus, Nix or service operation was performed.
